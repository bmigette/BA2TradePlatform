## 1. P1 — Small/mid market-cap ceilings never reach the live screener

The source screener base settings use `market_cap_max`. `live_settings_from_universe()` copies that key verbatim. It is not a defined live expert setting, and `StockScreener` reads only `screener_market_cap_max`. The live screener consequently uses its default `0`, meaning no ceiling.

| Instance | Intended ceiling | Effective live ceiling |
|---|---:|---|
| 7, large DS | None | None — correct |
| 8, mid Insider | $10 billion | None |
| 9, small EarningsDrift | $2 billion | None |
| 10, mid DS | $10 billion | None |
| 11, mid EarningsDrift | $10 billion | None |
| 12, small FMPRating | $2 billion | None |

The lower thresholds are carried correctly. Thus the small/mid labels currently do not describe bounded live market-cap bands. Because screening sorts by market cap, admitting larger companies can change the top-N selection substantially.

Repair: canonicalize both prefixed and unprefixed source screener keys to the live setting names, validate that every imported decision key is recognized, and compare the final screener filter dictionary after import. The concrete missing writes are `screener_market_cap_max=10000000000` for 8/10/11 and `screener_market_cap_max=2000000000` for 9/12.

Sources: `packages/common/ba2_common/core/deploy_parity.py:179`, `packages/providers/ba2_providers/StockScreener.py:44`, `packages/providers/ba2_providers/StockScreener.py:581`.

## 3. P1 — Boolean genes containing integer 1 reload as False

The save helper serializes a boolean-declared setting with `json.dumps(value)`. A GA integer `1` becomes the JSON string `"1"` in the ORM JSON column. On reload, the reader recognizes the string `"true"`, but not `"1"`; the effective boolean is therefore False.

Observed ON genes that are effectively OFF:

| Instance | Settings affected |
|---|---|
| 7 | `use_atr_stop`, `regime_overlay_enabled`, `screener_weinstein_stage2_only` |
| 8 | `regime_overlay_enabled` |
| 9 | `use_atr_stop`, `regime_overlay_enabled`, `screener_weinstein_stage2_only` |
| 10 | None; its three toggles are intentionally zero |
| 11 | `use_atr_stop`, `regime_overlay_enabled` |
| 12 | `use_atr_stop`, `regime_overlay_enabled` |

**The distinction matters:** the retained capped-run expert databases have the same false interpretation for ATR and regime toggles. Those are shared configuration/optimization defects, not evidence that live alone turned those features off. Simply enabling them in production would change the behavior that generated the recorded results.

The Weinstein toggle is a direct live-versus-backtest difference for 7 and 9: the backtest metric-store screen consumes the raw integer and applies the Stage-2 filter, while live screening receives False from the expert settings reader.

Repair: normalize valid boolean inputs before storage and support the legacy valid encodings on read, with a round-trip test through the real save/load path. Then rerun affected strategies under explicitly chosen effective settings. Preserve the old measurements and label corrected runs separately; do not silently reinterpret their performance as if these toggles had worked.

Sources: `packages/common/ba2_common/core/interfaces/ExtendableSettingsInterface.py:168-175` and `:392-409`; `packages/common/ba2_common/core/regime_overlay.py:99`; retained `run_1406/1407/1409/1420/1423/1425.sqlite` expertsetting rows.

## 4. P1 — Original optimized days differ from the recorded OK1000 days

There are two separate losses of schedule information:

1. The deploy exporter copies the optimization's base `run_schedule_override`, without overlaying `schedule:*` genes.
2. The rerun handler's `_GENE_PREFIXES` omits `schedule`. `run_ok1000.py` uses that rerun handler, so the capped tests used the base Monday schedule too.

The actual saved trade ledgers confirm this; the observation is not inferred solely from gene names:

| Instance | Original goal2020 trade-entry weekdays | Recorded OK1000 entry weekday | Current live entry weekday |
|---|---|---|---|
| 7 | Monday | Monday | Monday |
| 8 | Thursday | Monday | Monday |
| 9 | Wednesday, Thursday, Friday | Monday | Monday |
| 10 | Monday, Tuesday | Monday | Monday |
| 11 | Tuesday, Thursday, Friday | Monday | Monday |
| 12 | Monday, Wednesday, Thursday, Friday | Monday | Monday |

Some original genomes also enable weekend days, which produced no equity entries. The table shows actual observed trading weekdays.

Consequently, the current live entry cadence matches the measured OK1000 cadence, but five original goal2020 strategies were changed before their capped tests were measured. Their original-versus-capped performance comparison is not a pure capital-cap experiment. This qualifies the earlier candidate/combination reports.

Repair options:

- Preserve the optimized goal2020 schedule: fix schedule reconstruction, rerun at $1,000, and deploy the resulting complete effective configuration. This is my preferred research path.
- Preserve the measured OK1000 Monday variants: explicitly label them as Monday variants and retain Monday live entries. Still fix the screener differences and establish the intended boolean behavior.

## 5. P2 — The new importer schedule block only covers fresh instances

The schedule handling is inside `if created`. Re-importing into an existing instance does not apply `execution.run_schedule_override`, so the normal repair/redeploy path leaves an old or missing schedule untouched. A fresh instance with no schedule is enabled anyway; only a warning is printed.

The open-position cadence is also guessed from the entry times and weekdays. The exporter does not carry `manage_schedule_override`. That guess happens to match all six source management schedules here; it is not a general parity guarantee.

Repair: resolve and validate entry and management schedules before any DB writes, include both in the export, and apply the resolved schedules to new and existing targets. Missing or invalid execution configuration should fail before enabling an incomplete deployment. Include fresh-instance, existing-instance, and missing-schedule cases in tests.

Source: `tools/import_deploy_payload.py:145-173`.

## 6. Capital and historical-code qualifications

- Live instances currently use **60% of the same account's equity each**, not six independent fixed $1,000 caps. The sum of the virtual percentages is 360%; that is overlapping admission entitlement, not 360% of cash necessarily deployed. Real available-balance checks still apply. This is a portfolio-setting choice rather than an importer omission, but standalone cap results cannot establish shared-account parity.
- The five older capped-run DBs retain the old ATR/risk percentage assignments. Current source rows and live values contain the documented `_atr_swap_migration`, which accompanies a change to what those keys do. The current numeric payloads match. The historical DB numeric difference is **not** sufficient evidence to reverse that migration.
- The new capped FMPRating #1425 matches live ATR/risk values without that historical numeric difference.
- OK1000 rows retain copied genes and `equityCap`, but omit their optimization link and full standalone universe/execution configuration. Exporting directly from these rows cannot currently recover a complete deployment. Use a complete effective-config snapshot, rather than treating copied genes as a replayable artifact.
- The exporter leaves non-optimized decision defaults implicit. They match the inspected retained runs today, but future default changes can alter a redeployed winner without an obvious payload diff.
